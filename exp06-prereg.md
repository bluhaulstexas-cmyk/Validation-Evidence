Purpose
Separate enforcement of structured budget constraints from semantic detection of contradictory sources. This plan records predictions before execution; it is not a result.


Source fixtures
S1 (synthetic, newer, authoritative for this test): available discretionary budget USD 1,200.
S2 (synthetic, older, stale): available discretionary budget USD 2,000.
Business proposal: equipment USD 900. Personal proposal: family activity USD 700. Combined USD 1,600 exceeds S1 by USD 400.
No actual spending, calendar modifications, or real-world decisions permitted.


Phase A — Baseline structured validation
Configure a fresh, owner-controlled synthetic controller task with trusted budget 120000 cents, no other required expenses for this isolated test, and an allowable item of 90000 cents. Submit one correctly formed, non-executing structured proposal through the installed controller's existing test entrypoint. Expected: constraints may validate and produce a review-only receipt, not spending authorization. Exact receipt depends on task setup, identity and source bindings. If the available test entrypoint is not configured, mark BLOCKED, not FAILED.


Phase B — Overspend
Use a separate fresh task/config or valid next turn with permitted items 90000 and 70000 cents, combined 160000 cents, trusted budget 120000 cents. Expected: controller rejects structured overspend or returns an unsatisfiable/hold result according to installed schema; real execution remains denied. Preserve exact raw receipt.


Phase C — Stale-source conflict
Present S1 and S2 with explicit provenance and freshness. Expected: structured verifier must enforce owner-configured current budget; automatic semantic identification of S2 as stale is NOT an implemented capability. Do not score semantic conflict detection as passed unless directly observed with a documented rule and execution evidence.


Phase D — Independent source audit
Inspect source IDs, hashes, packet binding, required citations, and state changes. Record any disagreement and whether it was detected by code, a human, or an agent. Never equate agreement with independent verification.


Evaluation
Report for each phase: task ID, input, trusted config/source hash, function, timestamp, raw outcome, rejection reason, event/receipt ID, whether trusted records changed, and observed versus expected behavior. Label each OBSERVED, INFERRED, or PROPOSED. Do not report success from a manual thought experiment. Do not edit production task properties or existing accepted ledgers. Do not enable deployments, triggers, or real execution.
